# Отдельный ПСК на общем Linux-сервере

Это пакет **закрытого пилота**, не полноценный production и не автоматическое разрешение
подключать сотрудников к общему аккаунту. Исходный документ по-прежнему не открывается
из реестра; OCR/ИИ и роли пока не реализованы.

## Что изолировано

- Единственный Compose project: `das-psc-pilot`. Отдельный файл `compose.pilot.yml`,
  сеть `das-psc-pilot_psc_only` и том `das-psc-pilot_psc_data`.
- Порт-кандидат `127.0.0.1:18090`, до запуска проверяется. Другой порт задается `--port`.
- Максимум 1 CPU, 1 ГиБ RAM, swap не используется, 128 процессов, один worker,
  лимит конкурентных соединений 4, временные файлы до 320 МиБ (внутри лимита памяти).
- Никаких GPU: явный runtime runc, без devices/device requests. Не меняется
  конфигурация Nvidia/Docker на хосте. Нет общих томов, NAS, Docker socket и host network.
- Только свой том с метаданными. Root filesystem read-only, пользователь 10001,
  capabilities сняты; логи ограничены 3 файлами по 10 МиБ.
- Приложение запускается из **готового образа**, собираемого GitHub Actions. На целевом
  сервере нет pip install, docker build, apt upgrade или перезапуска общего daemon.
- Приватные логин/пароль пилота: пользователь `psc`, случайный пароль создается на сервере.
  `.state/config.json` имеет права 0600; каталог `.state` — 0700. Не присылайте его в чат,
  не публикуйте docker inspect / compose config с окружением и не включайте его в Git.

Контейнеры продолжают делить ядро, диск, память ядра и сеть хоста. Это не обещание
нулевого влияния и не защита от скомпрометированного Docker host. `internal`-сеть не
равна полному запрету связи с сервисами хоста через bridge. Для жесткой изоляции нужен
отдельный VM/узел. CPU/RAM-лимиты относятся к контейнеру, не к загрузке образа/IO daemon.
Рост тома SQLite не имеет жесткой дисковой квоты: контролируйте свободный диск,
число импортов и резервные копии; сначала один оператор и один объект.

## Порядок первого запуска

1. Проверить все результаты CI нужного commit. В Actions `Isolated pilot package`
   скачать артефакт `psc-isolated-pilot-<полный SHA>`. Только из этого репозитория и
   проверенного запуска: контрольная сумма защищает от порчи, не от подмены издателя.
2. Перенести содержимое в **новый отдельный** каталог `$HOME/das-psc-pilot`, не внутрь
   действующего DAS. Нужны `pilot.py`, `compose.pilot.yml`, `manifest.json`,
   `psc-image.tar.gz` и эта инструкция. Каталог доступен только оператору (0700).
3. Проверка без изменения сервисов:

   ```bash
   python3 pilot.py preflight
   ```

   При `BLOCKED` остановиться. Нельзя освобождать порт убийством процесса, обновлять
   Docker или чистить место командой prune. Проверяется локальный Linux Docker >=28,
   наличие лимитов, >=4 ГиБ свободной RAM, >=2 CPU, умеренная текущая load,
   >=10 ГиБ и >=10% свободного диска. Это консервативные условия пилота, не бенчмарк.
   Поддерживается локальный rootful Docker socket; remote/rootless contexts отклоняются.
   Существующие имена проекта, сети, тома тоже блокируют первый запуск.
4. После просмотра предварительного отчета и при разрешенном окне запуска:

   ```bash
   python3 pilot.py start --expect-commit ПОЛНЫЙ_ПРОВЕРЕННЫЙ_SHA
   ```

   Команда проверит SHA образа и deploy-файлов, загрузит образ, повторит preflight,
   сохранит baseline, сгенерирует пароль и запустит **только** `psc` этого проекта.
   Используется immutable локальный image ID, без pull/build и без auto-merge.
   Порт не резервируется между проверкой и запуском; при гонке Docker должен отказать,
   никакой чужой процесс не останавливается.
5. `PILOT_PASS` означает: фактические лимиты/монтирования/сеть проверены через inspect,
   healthcheck успешен, без пароля UI отвечает 401, с паролем — 200, состояние остальных
   контейнеров в контрольном снимке не изменилось. Это не полноценный нагрузочный тест
   DAS/Снабжения/ИИ. Проверить их привычные сценарии отдельно до/после и понаблюдать за
   CPU/RAM/IO. Через несколько минут повторить `python3 pilot.py verify`.

Пароль смотреть **локально** в `.state/config.json`. Скрипт не печатает его в лог.
После неуспешной приемки останавливается только созданный контейнер ПСК, том остается.
При сбое создания сохраняется `.state`; повторная установка его не перезаписывает.
Для разбора используется `verify`, не удаление данных. Первоначальный restart policy
`on-failure:3` не поднимает остановленный пилот после reboot: это сознательно закрытый
первый запуск, автозапуск согласовать после приемки.

## Доступ без изменения общего nginx

Порт на сервере доступен только через loopback. Для одного оператора используется
существующий SSH-доступ и шифрованный туннель; подставить уже проверенные SSH_HOST,
SSH_USER и SSH_PORT, а не придумывать новые реквизиты:

```bash
ssh -N -o ExitOnForwardFailure=yes -L 18090:127.0.0.1:18090 -p SSH_PORT SSH_USER@SSH_HOST
```

Браузер на рабочем компьютере: `http://127.0.0.1:18090`, логин `psc`.
HTTP здесь только на loopback внутри SSH-туннеля; в сеть пароль в открытом виде не
передается. Не открывать 18090 в firewall/роутере и не привязывать к `0.0.0.0`.
Для команды позже нужен отдельный HTTPS-вход и персональные права, не общий пароль.

## Остановка и данные

```bash
python3 pilot.py stop
```

Останавливает ровно один контейнер с проверенным Compose project/service label,
сохраняет том. Скрипт не обновляет существующую установку и не откатывает миграции.
До обновления отдельно зафиксировать старый image ID и проверить восстановление БД.
Не использовать `down -v`, `system prune`, `volume prune`, остановку всех контейнеров,
смену общих nginx/SSO/DAS/AI config или перезапуск Docker daemon.

SQLite backup делать через `sqlite3.Connection.backup`, а не копией одного sqlite-файла
при активном WAL. Затем вынести копию с сервера и проверить в отдельной тестовой папке/
контейнере. CI проверяет backup + восстановление на синтетической карточке; рабочая
backup-политика, внехостовое хранилище и эксплуатационная приемка пока не настроены.

Технические основания: Docker Compose services (cpus, mem_limit, memswap_limit,
pids_limit), Docker port publishing (localhost и требование Engine >=28), networks
(internal). https://docs.docker.com/reference/compose-file/services/
https://docs.docker.com/engine/network/port-publishing/
https://docs.docker.com/reference/compose-file/networks/
